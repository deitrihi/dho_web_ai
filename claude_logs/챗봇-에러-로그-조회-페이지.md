# 챗봇 서버 에러 로그 조회 페이지

## 요청
- "chat 서비스에서 서버 에러가 발생했는데, 에러로그를 조회 할 수 있는 페이지를 만들어줬으면 좋겠어"

## 확인
- 저장 방식을 "파일로 영구 저장(추천)" vs "메모리에만 보관" 중 선택받음 → 전자 선택
  (컨테이너 재시작/재배포에도 기록 유지).

## 조사
- `chat/app/api/chat/route.ts`에는 기존에 에러 처리/로깅이 전혀 없었음(try/catch 없음,
  streamText onError 미설정) — 스트리밍 중 에러가 나면 클라이언트엔 일반적인 "An error
  occurred." 메시지만 보이고 서버 쪽엔 stdout에만 찍혀서 `docker compose logs`로만
  확인 가능했음.
- 배포 구조상 `chat` 컨테이너는 `./:/data/dbsql:ro`(프로젝트 폴더 read-only)만 마운트되어
  있어 파일 쓰기가 안 됨 — 로그 저장용 별도 volume이 필요.

## 행동
- `chat/lib/error-log.ts` 신규: `logError(error, context)`(JSONL append) /
  `readErrorLogs(limit)`(최신순 파싱) 구현. 로그 경로는 `DHO_CHAT_LOG_PATH` 환경변수,
  기본값은 로컬 `.data/errors.jsonl`.
- `chat/app/api/chat/route.ts`: POST 핸들러를 `handleChat()`으로 분리하고 try/catch로
  감싸서 요청 파싱 등 스트리밍 시작 전 에러를 잡음(500 + 친절한 메시지 응답).
  `streamText`에 `onError: ({ error }) => logError(...)` 추가해서 스트리밍 중 에러
  (모델 API 에러 등)도 잡음.
- `chat/app/logs/page.tsx` 신규: 서버 컴포넌트(`dynamic = "force-dynamic"`)로
  `readErrorLogs()`를 직접 호출해 렌더링. 표 렌더링은 지난 작업에서 만든
  `JsonValue`(배열-of-객체 → 표)를 그대로 재사용 — 로그 항목의 `stack`을
  배열(줄 단위)로 저장해두면 `JsonValue`가 자동으로 불릿 목록으로 보여줌.
- `chat/app/page.tsx` 헤더에 "에러 로그" 링크 추가(`${basePath}/logs`).
- `docker-compose.yml`: `chat` 서비스에 named volume `chat_logs:/data/logs` 추가,
  `DHO_CHAT_LOG_PATH=/data/logs/errors.jsonl` 환경변수 설정. named volume을 쓴 이유 —
  bind mount로 `chat/` 하위에 두면 `deploy.sh`의 rsync가 매 배포마다 이 폴더를 건드릴
  위험이 있어서, 배포 전송과 완전히 분리된 Docker 자체 볼륨을 선택(컨테이너 재생성에도
  유지, 재빌드해도 안 지워짐).
- `chat/.gitignore`에 로컬 `.data/`(로그 기본 경로) 추가.

## 검증
- `npm run build`/`npm run lint` 통과. Turbopack이 `error-log.ts`의 동적 파일 경로
  (`path.join(process.cwd(), ...)` 폴백)를 두고 NFT 관련 경고 1건을 냄 —
  `/*turbopackIgnore: true*/` 주석을 추가해봤지만 경고 자체는 남음(빌드 실패는 아니고
  standalone 번들에 불필요한 파일이 약간 더 포함될 수 있다는 수준의 경고라 더 파고들지
  않음).
- 로컬 dev 서버(OPENAI_API_KEY 미설정 상태)로 실제 에러 2종 재현.
  1. 스트리밍 중 에러: `POST /api/chat`에 정상 메시지 전송 → `AI_LoadAPIKeyError`가
     `onError`로 잡혀 `.data/errors.jsonl`에 stack까지 포함해 기록됨 확인.
  2. 요청 파싱 에러: 깨진 JSON 바디로 `POST /api/chat` → 500 + `{"error":"서버 에러가
     발생했습니다."}` 응답, 같은 파일에 두 번째 항목으로 기록됨 확인.
  - `GET /logs` 200, 두 항목이 표(timestamp/message/stack/context 컬럼)로 렌더링되는
    것 HTML 응답에서 직접 확인.
- 테스트로 생성된 로컬 `.data/` 디렉토리는 정리함(gitignore 대상이라 커밋에는 안 잡히지만
  작업 흔적 제거 차원).

## 미해결
- 배포(NAS) 환경에서 named volume이 실제로 잘 마운트되고 `/chat/logs` 페이지가 동작하는지는
  다음 배포 시 확인 필요(`docker compose up -d --build chat`).
- 로그 조회 페이지에 인증이 없음 — 프로젝트 전체(webapp 포함)에 애초에 인증 시스템이 없어서
  기존 패턴을 따름. 필요하면 나중에 접근 제어 추가 검토.
