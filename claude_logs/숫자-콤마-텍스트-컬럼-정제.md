# 숫자 콤마 텍스트 컬럼 정제

## 요청
webapp/chat이 쓰는 구조화 DB에서 일부 숫자 컬럼이 "1,500"처럼 콤마를 포함한 채로 TEXT로
저장돼 있음. 콤마를 제거하고 숫자 타입으로 저장, 표시 시 세자리마다 콤마를 붙이는 별도
포맷 메소드를 만들어달라는 요청.

## 조사
- 조사 에이전트로 `dho_structured.sqlite3` 전체를 정규식 스캔해서 콤마 포함 숫자 컬럼
  전수 확인.
- 원인 1: `materialize_generic.py`의 정수 판별 정규식이 콤마 포함 문자열과 fullmatch가
  안 돼서 컬럼이 TEXT로 새고 원문 그대로(콤마 포함) 저장됨. 자동 생성 카테고리 테이블
  다수(courtRank, discovery, ganador, research 등) 영향.
- 원인 2: 관계 테이블(`build_relation_tables`)의 `{header}_text` 컬럼은 숫자 판별 없이
  무조건 TEXT로 고정 생성. `city__판매 아이템`, `portPermit__명성`, `ship__기본 성능`
  등 영향.
- 부수 발견: `materialize_cannon.py`에 콤마 문제보다 심각한 별도 버그 — 정규식이 콤마에서
  멈추는 첫 숫자 런만 잡아서 "1,032"가 관통력에 **1**로 잘못 저장(조용한 데이터 손상).
  raw_attrs 전수 재스캔으로 영향 범위가 `cannon.관통력` 하나뿐임을 실측 확인.
- webapp은 파생 테이블(cannon 등 211개)을 전혀 안 읽고 원문만 그대로 렌더링한다는 걸
  확인 -> 콤마 포맷을 실제로 적용할 지점은 챗봇 `run_sql`/`runSql` 결과뿐. 사용자에게
  AskUserQuestion으로 확인 후 이 경로로 확정, cannon 버그도 같이 고치기로 결정.

## 행동
- `materialize_generic.py`: `strip_commas()` 헬퍼 추가.
  - `build_category_table`: 정수 판별(`FULL_INT_RE.fullmatch`)과 삽입 시 값 파싱에 적용.
  - `build_relation_tables`: 헤더별 값을 먼저 모아 숫자 여부를 판별하는 2-pass 구조로
    재구성. 전부 숫자면 `{header}_num INTEGER`(콤마 제거 후 저장), 아니면 기존처럼
    `{header}_text TEXT` 유지.
- `materialize_cannon.py`: INT_COLUMNS 파싱 시 `text.replace(",", "")` 후 매칭하도록 수정.
- `dho_structured.sqlite3.bak-before-comma-fix` 백업 후 파생 스크립트 7개
  (`build_backlinks -> build_acquisition -> materialize_generic -> materialize_cannon ->
  materialize_recipe -> materialize_consumable -> materialize_tarotcard`, webapp의
  `rebuild_derived_tables()`와 동일 순서) 재실행.
- `openwebui_tool_dho_sql.py`: `format_number()` 추가, `run_sql` 반환 직전 각 row에 적용.
  `item_id`/`row_index`/`position`/`*_id` 식별자 컬럼은 제외(콤마 붙이면 수량으로 오해
  소지).
- `chat/lib/dho-db.ts`: `formatNumber()`로 동일 로직 포팅, `runSql`에 적용.

## 결정 및 이유
- 콤마 포맷 메소드는 웹앱 템플릿이 아니라 챗봇 `run_sql` 결과에 연결 — webapp이 파생
  테이블을 아예 안 읽고 원문만 렌더링하기 때문에 실제 "숫자를 표기"하는 지점이 여기뿐.
- 관계 테이블 컬럼명을 `{header}_num`으로 바꾼 이유: 타입(INTEGER)과 이름(`_text`)이
  불일치하면 혼란스러움. 하드코딩 참조하는 곳이 없어(전부 `SELECT *`/`get_table_schema`
  동적 조회) 안전하다고 판단.
- `run_sql` 포맷 적용 시 식별자 컬럼 제외: 이 스키마 전체가 FK/PK를 `*_id` 접미사로
  일관되게 명명하므로 안전한 휴리스틱.

## 검증
- 214개 테이블 전부 재생성 전/후 행 수 일치(데이터 유실 없음, 백업 DB와 직접 대조).
- `cannon.penetration` 절단 버그: item_id 8868/8869/8912/8927/8967을 raw_attrs 원문과
  대조해 정상값(1032/1204/1050/1200/1274)으로 복구 확인.
- `courtRank.명성`/`discovery.*`/`ganador.*`/`research.필요 페이지`/`portPermit__명성.*`/
  `ship__기본 성능.*` 등 전부 콤마 없는 INTEGER로 정상 전환 확인.
- Python(`run_sql`)/TS(`runSql`) 양쪽 실제 실행 결과: `item_id`는 그대로,
  `penetration`/`명성`은 `"1,500"` 형태 문자열로 반환됨을 직접 확인.
- webapp: Flask test_client로 `/`, `/cannon`, `/cannon/8868`, `/assistant` 200 확인.
- chat: `npm run lint`, `npm run build` 통과.

## 해결된 문제
- 콤마 포함 숫자 컬럼의 TEXT 오분류.
- `materialize_cannon.py`의 관통력 절단 데이터 손상 버그(부수 발견, 사용자 승인 후 수정).

## 미해결
- `city__판매 아이템.발전도_text`/`투자_text`는 재생성 후에도 TEXT+콤마 그대로 남음 —
  원본 데이터가 같은 헤더명 아래 숫자 투자 금액과 "필요" 텍스트 플래그를 섞어 쓰고 있어서
  숫자만 남기면 정보 손실이 생기기 때문에 의도적으로 TEXT 유지(회귀 아님, 로직이 올바르게
  "전부 숫자는 아님"을 판별한 결과). 나중에 필요하면 표를 손으로 분리하는 별도 작업으로
  처리 가능.
- `dho_structured.sqlite3.bak-before-comma-fix`(256MB) 백업 파일은 정리 안 하고 남겨둠 —
  커밋 대상 아님, 안정성 확인되면 사용자가 직접 삭제 가능.
- `tarot_card`/`tarotCard` 테이블명 불일치는 여전히 미해결(이전 세션부터 알려진 이슈,
  이번 작업과 무관).
