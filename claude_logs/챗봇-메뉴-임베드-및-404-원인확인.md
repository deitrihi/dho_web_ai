# 사이드바 chat.ai 메뉴 추가 + 기존 /chat 404 원인 확인

## 요청
- webapp 왼쪽 사이드바 하단에 "chat.ai" 메뉴를 추가하고, 클릭하면 `/chat`이 컨텐츠 영역에
  나오도록 해달라는 요청
- 이전에 `/chat`에서 챗봇 사이트가 404를 뱉었던 문제(그래서 Next.js `basePath` 작업을
  했던 것)도 같이 확인해달라는 요청

## 원인 확인
- 이미 되어 있던 `NEXT_BASE_PATH=/chat` 작업(chat/next.config.ts, chat/Dockerfile,
  docker-compose.yml)은 챗봇 컨테이너 자체가 `/chat` 하위경로에서 올바르게 응답하도록
  하는 수정으로, 이미 정상 동작 확인된 상태였음(CHANGELOG.md 기존 항목 참고)
- 그런데 `dho_webapp.py`의 `@app.route("/<category>")` 캐치올 라우트가 `/chat`을
  "chat"이라는 카테고리 조회로 먼저 가로채서, 존재하지 않는 카테고리라 `abort(404)`를
  반환하고 있었음 — 사용자가 실제로 겪은 404는 이 Flask 라우트 충돌이 원인이었음

## 사용자 확인 사항 (AskUserQuestion)
- 챗봇 표시 방식: iframe으로 사이드바 레이아웃 안에 임베드 (추천안 선택)
- 챗봇 접근 주소: webapp과 같은 도메인, 리버스 프록시가 `/`→webapp, `/chat`→chat
  컨테이너로 통합 라우팅하는 구성 확인

## 결정 및 구현
- webapp이 `/chat`을 직접 라우트로 쓰면 운영 환경에서 리버스 프록시가 그 경로를 그대로
  챗봇 컨테이너로 넘기는 것과 충돌하므로(그리고 캐치올 라우트와도 충돌), wrapper 페이지는
  `/chat-ai`라는 별도 경로에 두고 그 안의 `<iframe>`만 실제 챗봇 주소(`/chat`)를 가리키게 함
- `dho_webapp.py`: `CHAT_URL = os.environ.get("DHO_CHAT_URL", "/chat")` 추가, `/chat-ai`
  라우트에서 `chat.html` 렌더링
- `templates/chat.html` 신규: `base.html` 확장, breadcrumb 숨기고 content 블록에 iframe
- `templates/base.html`: 사이드바 nav 아래 `.sidebar-footer`에 "chat.ai" 링크 추가
  (flex:1인 `.sidebar-nav`가 남는 공간을 채워서 자연히 하단에 고정됨)
- `static/style.css`: `.sidebar-footer`/`.sidebar-footer-link`, `.chat-frame`(컨텐츠
  영역을 꽉 채우는 iframe) 스타일 추가

## 검증
- `python dho_webapp.py` 로컬 실행 후 curl로 확인: `/` 200, `/chat-ai` 200(iframe 포함),
  기존 `/chat`은 여전히 404(캐치올 라우트가 처리 — 운영에서는 리버스 프록시가 먼저
  가로채므로 실제로는 도달 안 함)
- 사이드바 렌더링 결과에 `chat.ai` 링크와 `/chat-ai` href 정상 확인

## 미해결 / 참고

  테스트 못 함(리버스 프록시가 로컬에 없음) — 필요하면 `DHO_CHAT_URL=http://localhost:3000/chat`

## 후속 수정 (2026-08-04)
- 사용자가 `python dho_webapp.py`로 로컬에서 바로 띄워서 확인하다가, chat.ai 클릭 시
  `localhost:3000/chat`(chat 컨테이너)이 아니라 `localhost:5050/chat`(webapp 자신)으로
  가고 있다고 알려줌
- 원인: `DHO_CHAT_URL` 기본값이 `/chat`(상대경로)였는데, 로컬엔 리버스 프록시가 없어서
  이 상대경로가 iframe이 로드된 현재 페이지 origin인 `localhost:5050`으로 풀려버림 →
  webapp 자신의 캐치올 라우트가 받아서 다시 404
- 수정: 기본값을 로컬 실행 전제로 뒤집음 — `DHO_CHAT_URL` 기본값을
  `http://localhost:3000/chat`으로 변경(dho_webapp.py), 대신 `docker-compose.yml`의
  webapp 서비스에 `DHO_CHAT_URL=/chat` 환경변수를 추가해서 운영(리버스 프록시 뒤) 배포
  시에는 상대경로로 명시적으로 되돌림. `DHO_DB_PATH`와 동일한 관례("로컬 기본값 + 컨테이너
  환경변수로 오버라이드")
- 검증: 로컬 `python dho_webapp.py` 재기동 후 `/chat-ai` 응답에서
  `iframe src="http://localhost:3000/chat"` 확인

## 후속 수정 2 (2026-08-04, 실제 NAS 배포에서 재발)
- 사용자가 실제 NAS 배포(`192.168.0.200:5050`)에서 chat.ai 클릭 → 스크린샷으로 Flask
  "Not Found" 페이지 + devtools에서 iframe이 `src="/chat"`로 `192.168.0.200:5050/chat`을
  가리키고 있는 것 확인해서 공유해줌
- 사용자 설명으로 실제 배포 구조 파악: webapp은 5050 포트로 직접 접속(리버스 프록시 안
  거침), chat은 별도로 nginx가 `/chat`을 3000 포트로 포트포워딩 — 즉 webapp/chat이 같은
  도메인으로 통합된 게 아니라 완전히 분리된 두 개의 진입점. 전전 수정에서
  `docker-compose.yml`에 넣은 `DHO_CHAT_URL=/chat`(통합 리버스 프록시 전제)도,
  `http://localhost:3000/chat` 기본값(로컬 hostname 고정)도 둘 다 이 실제 구조와
  안 맞았음
- 근본 수정: 서버가 host를 문자열로 고정해서 넘겨주는 방식 자체를 버리고, 브라우저에서
  `location.hostname`을 그대로 재사용해서 iframe src를 조립하도록 변경
  (`templates/chat.html` 인라인 스크립트). 서버는 포트만 `DHO_CHAT_PORT`(기본 `3000`)로
  넘겨줌 — `dho_webapp.py`의 `CHAT_URL` → `CHAT_PORT`로 변경, `docker-compose.yml`의
  webapp 환경변수 오버라이드(`DHO_CHAT_URL=/chat`)는 필요 없어져서 제거
- 이 방식이면 localhost/LAN IP(192.168.0.200)/향후 실제 도메인 등 접속 주소가 뭐든
  상관없이 "지금 접속한 호스트의 3000 포트"로 항상 정확히 붙음
- 검증: 로컬 `python dho_webapp.py`에서 `/chat-ai` 응답에 `id="chat-frame"` iframe +
  `location.hostname` 기반 조립 스크립트 포함 확인 (실제 NAS 재현은 사용자가 재배포 후
  확인 필요)

## 후속 수정 3 (2026-08-04, 실제 진입 경로 재확인 후 최종 정리)
- 사용자가 nginx 설정 전체를 공유: 외부 접근은 도메인 443 하나로만 들어오고, nginx가
  `location /` → `192.168.0.200:5050`(webapp), `location /chat` → `192.168.0.200:3000`
  (chat)으로 나눠 프록시함 — 즉 **바로 전 수정에서 전제했던 것과 반대로, 실제 운영
  진입점은 nginx이고 webapp/chat이 이미 같은 origin(도메인+443)으로 통합돼 있음**.
  후속 수정 2의 `location.hostname:3000` 방식은 브라우저가 `도메인:3000`으로 직접 붙으려
  하는데 외부에 3000 포트가 안 열려 있어서 실패하고 있었음 (IP:5050 직접 접속은 nginx를
  안 거치는 로컬/LAN 테스트 경로였던 것으로 재확인)
- 최종 정리: 후속 수정 2를 되돌리고 최초 설계로 복귀 — `dho_webapp.py`는 다시 `CHAT_URL`
  환경변수(기본값 `/chat`)를 쓰고, `templates/chat.html`도 단순 `<iframe src="{{ chat_url }}">`
  로 되돌림. 상대경로 `/chat`이면 nginx가 같은 origin 안에서 알아서 chat 컨테이너로
  넘겨주므로 브라우저가 포트를 몰라도 됨. nginx 없이 webapp만 직접 띄워 테스트할 때는
  `DHO_CHAT_URL=http://<host>:3000/chat`처럼 절대경로로 오버라이드
- 검증: 로컬에서 기본값(`/chat`)과 `DHO_CHAT_URL` 오버라이드(`http://localhost:3000/chat`)
  둘 다 `/chat-ai` 응답의 iframe src에 그대로 반영되는 것 확인
- 교훈: nginx 설정처럼 이 저장소에 없는 외부 인프라 정보는 스크린샷/설명만으로 구조를
  추측하지 말고, 실제 conf 내용을 먼저 요청해서 확정한 뒤 수정했어야 왕복을 줄일 수
  있었음

## 후속 수정 4 (2026-08-04, /chat-ai 404 — nginx 접두어 매칭 충돌)
- 사용자가 `/chat-ai`로 접근하니 404가 난다고 알려줌
- 원인: nginx의 `location /chat`은 접두어(prefix) 매칭이라 `/chat-ai`처럼 "chat"으로
  시작하는 모든 경로가 이 규칙에 걸림 — nginx가 `/`(1글자)와 `/chat`(5글자) 중 더 긴
  접두어인 `/chat` 쪽을 선택해서 `/chat-ai` 요청을 chat 컨테이너(포트 3000)로 그대로
  넘겨버림. chat 컨테이너(Next.js, basePath `/chat`)에는 `/chat-ai`라는 라우트가
  없으니 거기서 404가 남 — webapp(Flask)까지는 요청이 오지도 못하는 상태였음
- 수정: nginx를 다시 건드리는 대신, wrapper 라우트 자체를 "chat"으로 시작하지 않는
  경로로 옮겨서 이 충돌을 원천 차단 — `dho_webapp.py`의 라우트를 `/chat-ai` →
  `/assistant`로 변경(뷰 함수명 `chat_ai`는 그대로라 `templates/base.html`의
  `url_for('chat_ai')` 링크는 코드 수정 없이 자동으로 `/assistant`를 가리키게 됨)
- 검증: 로컬에서 `/assistant` 200, 옛 경로 `/chat-ai`는 (라우트 자체가 없어져서) 404,
  사이드바 링크가 `href="/assistant"`로 렌더링되는 것 확인
