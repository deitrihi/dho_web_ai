# 3단계(로컬 LLM 연동) 마무리 + 4단계(로컬 웹앱) 시작

## 요청
- OpenWebUI + 로컬/외부 LLM으로 Text-to-SQL 질의응답 구현 (3단계 이어서 진행)
- 실사용 테스트 중 나온 버그들 원인 파악 및 수정
- API(Claude/OpenAI) 비용 문의
- 크롤링한 데이터로 원본 사이트와 동일한 정보 구조의 웹사이트 제작 요청
- 카테고리명이 영문으로만 보이고 대분류가 없다는 피드백 → 한글 로컬라이제이션 요청

## 행동 요약 (시간순)

### OpenWebUI Tool 개발 및 디버깅
- `openwebui_tool_dho_sql.py` 신규 작성: `list_categories`/`find_tables`/`get_table_schema`/
  `run_sql` 4개 함수로 시작, read-only 커넥션 + SELECT 전용 + 세미콜론 인젝션 차단
- 로컬 모델 `exaone3.5:7.8b`가 tools capability 없어서 `qwen2.5:7b`로 교체
- 실사용 테스트("준사관 우대 스킬") 중 발견: 모델이 아이템 이름(데이터 값)을 테이블 이름으로
  착각 → `search_items` 추가
- 이어서 발견: 모델이 search_items 성공 후 다음 단계(get_table_schema→run_sql)로 못 이어감
  (로컬 소형 모델의 다단계 도구 체이닝 약점) → 이름검색+상세조회를 한 번에 하는
  `get_item_detail`을 1순위 함수로 추가
- OpenWebUI 설정 트러블슈팅: 함수 호출 텍스트가 그대로 노출되는 문제 → Function Calling
  모드를 Native로 전환 안내, 불필요한 내장 도구(메모/캘린더 등) 비활성화 안내

### 인프라 전환 (Ollama → 외부 API)
- API 비용 문의 대응: Claude API 가격표, OpenAI API 가격표 조사 후 안내
  (자세한 내용은 `claude_logs/nas-이전-compose-수정.md` 참고 — 이 파일과 시기가 겹침)
- 사용자가 OpenAI API 키 발급 → `docker-compose.yml`에서 GPU 필요한 ollama 서비스 제거,
  OpenAI 호환 엔드포인트(`OPENAI_API_BASE_URL`/`OPENAI_API_KEY`)로 전환, 기본 모델 `gpt-5-mini`

### 숨은 탭 스크래핑 버그 발견 및 수정 (가장 큰 작업)
- gpt-5-mini로 재테스트 중 "해양조합 등록증을 해상 NPC로 얻을 수 있나?" 질문에 DB에 없다고
  오답 → 원인 조사
- **근본 원인**: 원본 사이트의 "획득 방법" 섹션이 탭 UI(퀘스트/아이템 사용/해상 NPC 등)인데,
  기존 `scraper.py`(순수 HTTP)는 기본 활성 탭 표만 캡처하고 나머지 탭은 데이터 자체가
  응답에 없음. 라이브 사이트 직접 재확인으로 캐시 문제 아님을 확인, 임베디드 JSON도 없어서
  헤드리스 브라우저 필요하다고 판단
- 전수 스캔: 33,496건 중 **3,365건(약 10%)** 영향 확인 (consumable/equipment/tradeGoods/
  field/city/sea/cannon 등에 집중)
- `scrape_hidden_tabs.py` 신규 작성 (Playwright): 영향 항목만 방문해서 비활성 탭 클릭 →
  `build_structured_db.extract_detail()` 재사용해서 새 표/속성만 raw_tables/raw_attrs에 추가.
  `hidden_tabs_progress` 테이블로 재실행 시 이어서 진행 가능
- 첫 실행이 특정 항목에서 hang(CPU 사용량 0인 채 수 시간 정체) → 강제 종료 후 개별 항목
  45초 데드라인 + Playwright 기본 타임아웃 10초 + 200건마다 page 재생성으로 보강, 재실행
- 전체 3,365건 완주 (오류 0건, 1,210건에서 신규 데이터 발견)
- `build_acquisition.py`/`materialize_generic.py`/`materialize_consumable.py`/
  `materialize_cannon.py` 재실행으로 최종 테이블까지 반영. 해양조합 등록증 케이스
  (해상 NPC 78건) 정상 반영 확인 — 최초 버그 리포트 해결

### get_item_detail 추가 개선
- DB 수정 후에도 gpt-5-mini가 여전히 "없다"고 오답 → 원인: `get_item_detail`이 카테고리
  전용 테이블(certificate 등)만 조회하고, `item_acquisition_marine_npc_sea` 같은 공유
  관계 테이블은 자동으로 안 붙여줌 (모델이 멀티테이블 조인을 스스로 알아내야 하는 구조)
- `_acquisition_info()` 헬퍼 추가: `item_acquisition_*`/`item_transmutation_*` 전 테이블을
  category+item_id로 자동 조인해서 `get_item_detail` 결과의 "획득_방법" 필드에 통째로 반환
- 해양조합 등록증 케이스로 검증(marine_npc 77건 NPC명/함대수 포함, marine_npc_sea 78건,
  from_item 7건까지 한 번에 반환)

### 4단계: 로컬 조회용 웹앱
- 사용자 요청: "크롤링한 사이트와 동일한 사이트를 만들어줄 수 있을까?"
- 방향 확인(AskUserQuestion): 동적 웹서버(Flask) / 정보구조만 동일·디자인은 간결하게 새로
  작성 / 소규모 샘플(cannon)로 먼저 확인
- `dho_webapp.py` + `templates/`(base/index/category/item) + `static/style.css` 신규 작성.
  `items_core`/`raw_attrs`/`raw_tables`가 원본 페이지를 1:1로 옮겨온 스테이징 데이터라
  (숨은 탭 보강분 포함) 이 세 테이블만으로 렌더링 가능함을 활용
  - 같은 label의 표가 여러 개면("획득 방법" 등) 첫 헤더로 구분되는 이름을 자동으로 붙임
    (예: "획득 방법 — 해상 NPC")
- 로컬 실행(:5050) 검증: 카테고리 목록/cannon 목록/certificate 1898 상세 200 확인,
  marineNpc/sea로 상호 링크 이동, 없는 카테고리 404 확인

### 카테고리 한글 로컬라이제이션
- 피드백: "정보가 다 영어로 보이고, 카테고리 대분류가 적용이 안됨. DB엔 없는 데이터일 수도
  있으니, 참조 사이트 보고 대분류/카테고리명 한글로 변경, **별도 테이블에 저장하는
  로컬라이제이션 방식**으로 해달라"
- 원본 사이트가 배포하는 정적 JS 번들(`/assets/categories-*.js`)에 카테고리 한글명(`bt`
  객체)과 대분류 그룹 6개(`xt` 배열: 모험/아이템/선박/인물 · 스킬/NPC/세계) 매핑이 그대로
  하드코딩돼 있는 것을 발견 — 이 값을 그대로 옮겨옴
- `build_category_localization.py` 신규 작성: `category_localization` 테이블(slug,
  label_ko, group_title_ko, group_flag, group_order, order_in_group) 생성.
  DB의 실제 category 70개와 전수 대조 — 누락/불일치 0건
- `dho_webapp.py`가 이 테이블을 조인해서 홈 화면 대분류 그룹핑 + 카테고리/브레드크럼
  한글 표시하도록 수정
- equipment(장비품)/ship(선박)/cannon(대포)/certificate(추천장) 등 여러 카테고리로
  검증 완료 — 홈 화면뿐 아니라 목록/상세 페이지 전체에 적용됨 확인

## 결정 사항
- Text-to-SQL 접근에서 로컬 소형 모델(qwen2.5:7b)의 멀티스텝 도구 체이닝 한계를
  "더 똑똑한 프롬프트"가 아니라 "도구 설계를 단순화"하는 방향으로 해결 (get_item_detail이
  검색+조회+조인을 한 번에 처리)
- 웹앱 디자인은 원본 CSS를 따라하지 않고 정보 구조만 동일하게, 스타일은 간결하게 새로 작성
- 로컬라이제이션은 원본 raw 데이터를 건드리지 않고 별도 테이블로 분리 (표시 시점에만 참조)
